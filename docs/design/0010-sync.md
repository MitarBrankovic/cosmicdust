# 0010 — Sync: whole files, probed and continued, at least once into an idempotent receiver

**Status:** accepted

The unit of sending is a finished Parquet file of the store, as written: already compressed, not compressed again. A
file goes in chunks (256 KiB) that each carry the file's reference - node, table, partition, name, size, CRC-32C,
rows, time range - so the receiver keeps no session beyond the partial file. It writes the file under a temporary
name, checks size and CRC, fsyncs and renames it, and only then answers `stored`. A file it already holds with the
same size and CRC is a `duplicate`. The node marks a file synced on either answer, so every file is sent at least
once and stored exactly once, without a coordinator (a prototype held this through 34 crashes of the agent, 4 of the
control plane and a 10-minute outage; end to end on Docker, 18,000 lines through 4 kills of the node, 1 of the
receiver and a 20 s outage, on both transports).

Every file starts with a probe, a chunk without data. It tells whether the receiver is there - a NATS broker takes
messages whether or not anybody listens, and without the probe every retry during an outage sent a file into the
void - whether it already has the file, and how much of it arrived before an upload broke off: the upload
continues from there. Starting over had made a narrow lossy link a loop that never delivered a file. Each
upload attempt carries a random ID, and the probe hands the file to its attempt: the receiver refuses chunks of any
other. Chunks of a cancelled gRPC stream still in flight had grown the copy past what the probe answered, and the
next attempt's first chunk was refused as out of order.

Two transports carry the same protocol (`pkg/api`) behind `cosmicdust.Transport`, picked by the scheme of the sync
URL: gRPC, which the services of the control plane speak, and NATS. NATS
publishes chunks on `<prefix>.files.<node>` with a reply subject, keeps 32 in flight once the probe has been answered
(about the bandwidth-delay product) and waits for each next ack up to 30 s: every ack is progress, so a slow
link needs time for one chunk, not for the file. gRPC sends a unary probe, then one client stream per file, and
relies on HTTP/2 flow control. Urgent events - a container that died with an error or for memory, once per
incarnation although both runtimes report it - go on a connection of their own, so that they do not wait behind a
file in the socket buffers (p95 2-22 s on the files' connection, 0.3-0.5 s on their own). They are a
shortcut: the same events reach the control plane with the events table. For the containers Docker runs, Docker's
own exit decides whether one is urgent: it comes after any kill Docker was asked for, and an exit after one (docker
stop, restart, rm -f, compose down) is a stop, not a crash. containerd reports the exit ~350 ms earlier and cannot
tell; for the containers only containerd runs, every exit with an error is urgent.

The engine runs every 10 s in the node's process and takes files through `Store.Claim`, which keeps compaction away
from them. A claim does not survive a crash, so the first one also records the file as offered in its manifest,
before the file leaves: an offered file may be at the control plane with its answer lost, and compaction leaves it
alone, or its rows would arrive a second time in the merged file. A round that cannot reach the control plane stops,
and retries with backoff and jitter (1 s to 60 s). The transport says when its connection comes back - the NATS
client reconnects every second, the gRPC connection is kept connecting at most 10 s apart - and the engine sends at
once rather than at the end of its backoff, up to a minute after a long outage. A file the control plane refuses (a
CRC mismatch, say) stays unsynced and is offered again, but no longer holds up the files behind it. Carrying the
protocol over a connection the node already holds would change the transport, not the engine.
