# 0006 — The WAL: positions in the block, one fsync per pass

**Status:** accepted

Log records and lifecycle events land in a write-ahead log before anything else, in blocks: a header with a CRC
over an s2-compressed binary payload (JSON blocks, tried first, cost five to eight times more to write
and read). A block also holds, for each container in it, where reading its log resumes. Data and position become
durable in the same fsync, so a restart resumes exactly after the last record written: no gap, no duplicate. The
crash test kills the reader-and-WAL process with SIGKILL ten or more times while the log keeps growing and
rotating, and every line is in the WAL exactly once; so does the daemon on a real Docker host.

A block names each of its containers once, with name, image and application as the tracker knew them when the
lines were read, so the conversion still has them for a container removed long ago. The container's state at each
line is not stored: it is decided at conversion, when late events are in.

Segments are sealed at 8 MiB or 5 s and handed to the consumer, which releases them once it has committed what they
held; before they go, the positions as of the release are written to a checkpoint. Recovery cuts a torn block off
the newest segment, reports damage in older ones, and finds every position from the checkpoint and the segments
still on disk. A write that fails for lack of space is cut back off the segment, its block waits in memory and is
written once by the next flush; the tailer stops reading meanwhile, and nothing is lost or doubled.

The WAL is also where the lifecycle tracker finds the events its state on disk does not have yet. The tracker saves
its state a second after a change, so a kill -9 in that second lost the change, and the listing after the restart
inferred the event once more although it was stored already (record 0004). At its start the tracker applies again the
events of the blocks written since shortly before its state on disk (a minute, for a clock that stepped back), and a
released segment stays until the tracker's state on disk is newer than its last block, ten minutes at most: a
segment converted in that second would otherwise be gone with its events. Older blocks are in that state already, or
are about a container removed and forgotten since, which a replay would bring back.

One pass of the tailer is one block. The tailer aligns the deadlines of its files to a common grid, so the files due
at about the same time make one pass: unaligned, ten files made ~40 fsyncs a second, ~8 % of a core and 0.76 bytes
written per byte read; aligned, 4 a second, 1.6 % and 0.22.
